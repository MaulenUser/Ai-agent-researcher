# Состояния и жизненные циклы

**Дата среза:** 2026-08-31.

> **AS IS: состояний не существует.** Кода нет, ни один enum не объявлен.
>
> **Важное ограничение источника:** ПЗ **не содержит ни одной диаграммы состояний и ни одного закрытого перечня статусов**, кроме классов ссылок (§9) и классов релевантности (§12). Раздел §6 перечисляет *обрабатываемые ситуации* (redirect, 404, 403, timeout, SSL error, unsupported content type), но не сопоставляет им значения поля `status` и показывает лишь одно значение — `"accessible"`.
>
> Поэтому ниже разделены два типа содержимого: **зафиксированное в ПЗ** и **`PROPOSAL`** — техническое предложение, требующее утверждения. Реализовывать `PROPOSAL` как утверждённое запрещено.

## Что зафиксировано в ПЗ

### Класс ссылки (закрытый перечень, ПЗ §9)

```
HIGH_VALUE | POTENTIALLY_RELEVANT | NAVIGATION | IRRELEVANT
```

Переходов между классами нет: класс присваивается один раз при классификации (BR-005). **Обновлено 2026-08-31:** классов пять — к четырём из ПЗ §9 добавлен внутренний `UNKNOWN` ([D-036](../01_PRODUCT/decisions.md#d-036); ПЗ §9 требует «минимум четыре»). `IRRELEVANT` присваивается только по положительному признаку и никогда как остаток. Полные правила присвоения — [link-taxonomy.md](../01_PRODUCT/link-taxonomy.md).

### Класс релевантности документа (закрытый перечень, ПЗ §12)

```
HIGH | MEDIUM | LOW
```

Переходов нет: оценка присваивается один раз. Из HIGH и MEDIUM извлекается evidence (BR-006). Пороги — [OQ-003](../01_PRODUCT/open-questions.md#oq-003).

### Статус PDF-скана (ПЗ §11)

Единственное явно названное значение статуса документа: `ocr_required`. Означает, что текст извлечь не удалось, OCR на MVP не выполняется, обработка прочих документов продолжается (BR-009). Критерий срабатывания — [OQ-017](../01_PRODUCT/open-questions.md#oq-017).

### Глубина обхода (ПЗ §10)

Не состояние, но параметр жизненного цикла документа:

```
depth 0 — seed URL
depth 1 — ссылки с seed-страницы
depth 2 — ссылки с найденных релевантных страниц (терминальный уровень)
```

Документ получает `depth` один раз при обнаружении. Повторная встреча того же canonical URL на другом уровне не создаёт новый документ (BR-004); какой `depth` сохраняется при этом — ПЗ не уточняет.

## PROPOSAL: жизненный цикл URL

**Статус: `PROPOSAL`. Не утверждено.** Основание для предложения — перечень обрабатываемых ситуаций ПЗ §6 плюс требования REQ-002, REQ-003, REQ-005. Утверждение — [OQ-024](../01_PRODUCT/open-questions.md#oq-024).

```
                   DISCOVERED
                        │
             ┌──────────┼──────────┐
             │ (BR-010) │          │ (BR-004 / BR-013)
             ▼          ▼          ▼
         REJECTED   VALIDATED   SKIPPED_DUPLICATE
                        │
                        ▼
                    CHECKING
                        │
     ┌──────┬───────┬───┴───┬────────┬─────────────┐
     ▼      ▼       ▼       ▼        ▼             ▼
ACCESSIBLE NOT_  FORBIDDEN TIMEOUT SSL_ERROR  UNSUPPORTED_
     │     FOUND                                CONTENT_TYPE
     ▼
  FETCHED
     │
     ▼
   PARSED ──► ASSESSED ──► (evidence extracted, если HIGH/MEDIUM)
     │
     └──► PARSE_FAILED / OCR_REQUIRED
```

Соответствие состояний ситуациям ПЗ §6:

| Ситуация ПЗ §6 | Предлагаемое состояние | Комментарий |
|---|---|---|
| HTTP 200 | `ACCESSIBLE` | Единственное значение, названное в ПЗ (`"accessible"`) |
| redirect | `ACCESSIBLE` с заполненным `final_url` | ПЗ требует «обработку redirects» (§21), а не отдельный статус. Трактовка, требует подтверждения |
| 404 | `NOT_FOUND` | Имя предложено |
| 403 | `FORBIDDEN` | Имя предложено |
| timeout | `TIMEOUT` | `http_status` отсутствует — поведение поля не описано |
| SSL error | `SSL_ERROR` | `http_status` отсутствует |
| unsupported content type | `UNSUPPORTED_CONTENT_TYPE` | Перечень поддерживаемых типов — HTML и PDF (ПЗ §4) |

Состояния `REJECTED` (нарушение BR-010), `SKIPPED_DUPLICATE` (BR-004/BR-013), `FETCHED`, `PARSED`, `PARSE_FAILED`, `ASSESSED` в ПЗ **не упоминаются вовсе** — это чисто техническое предложение для внутреннего конвейера. Попадают ли они в поле `status` итогового JSON (`sources[]`, ПЗ §14) или остаются внутренними — часть [OQ-024](../01_PRODUCT/open-questions.md#oq-024).

## PROPOSAL: жизненный цикл документа

**Статус: `PROPOSAL`.**

```
DISCOVERED ──► CLASSIFIED ──► FETCHED ──► PARSED ──► ASSESSED ──► EVIDENCE_EXTRACTED
     │              │             │           │           │
     │              ▼             ▼           ▼           ▼
     │        (NAVIGATION/    FETCH_      OCR_REQUIRED  (LOW → evidence
     │        IRRELEVANT →    FAILED      PARSE_FAILED   не извлекается,
     │        не обходится)                              BR-006)
     ▼
LIMIT_EXCEEDED (BR-003)
```

Терминальные состояния: `EVIDENCE_EXTRACTED`, `FETCH_FAILED`, `OCR_REQUIRED`, `PARSE_FAILED`, `LIMIT_EXCEEDED`, отбрасывание по классу ссылки.

**Не определено:**

- отражается ли документ в `discovered_documents[]` итогового JSON, если он не дошёл до `ASSESSED` — [OQ-027](../01_PRODUCT/open-questions.md#oq-027);
- останавливает ли `LIMIT_EXCEEDED` обход только текущего seed или всё исследование, и помечается ли результат усечённым — см. [workflow.md, сценарий S-05](../01_PRODUCT/workflow.md#сценарий-s-05-достижение-лимита-обхода);
- какое состояние получает документ при отказе LLM на стадии оценки — [OQ-006](../01_PRODUCT/open-questions.md#oq-006).

## Жизненный цикл исследования

**Статус: `PROPOSAL`.** ПЗ описывает исследование как единичный запуск CLI (§27) без промежуточных состояний, возобновления или отмены.

```
STARTED ──► CRAWLING ──► ANALYZING ──► SYNTHESIZING ──► COMPLETED
                                                    └─► FAILED
```

Состояние `FAILED` для всего исследования в ПЗ не предусмотрено: BR-001 требует продолжать работу при отказе отдельных URL. При каких условиях исследование считается несостоявшимся целиком — не определено ([OQ-006](../01_PRODUCT/open-questions.md#oq-006)).

Возобновление прерванного исследования, отмена, повторный запуск с сохранением прогресса в объём MVP не входят (ПЗ §4, §26).

## Что запрещено делать на основании этого документа

1. Реализовывать `PROPOSAL`-состояния как утверждённые и выносить их в публичный JSON-контракт до закрытия [OQ-024](../01_PRODUCT/open-questions.md#oq-024).
2. Добавлять состояния, отсутствующие и в ПЗ, и в предложениях выше.
3. Переименовывать закрытые перечни ПЗ (классы ссылок, классы релевантности, `ocr_required`).
