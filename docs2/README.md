# docs2 — рабочая документация проекта Macroprud (Regulatory Research Agent)

## Назначение docs2

`docs2/` — актуализированный контекст для разработчиков и AI-агентов. Документация решает четыре задачи:

1. Отделить **целевые требования (TO BE)** от **фактического состояния кода (AS IS)**.
2. Зафиксировать подтверждённые решения, предположения и открытые вопросы.
3. Связать требования → бизнес-правила → расхождения → задачи → код → тесты.
4. Не дать следующему агенту **придумать** отсутствующую бизнес-логику.

`docs2/` не заменяет ПЗ. ПЗ остаётся первоисточником, `docs2/00_SOURCE/business-requirements.md` — его нормализованная версия с идентификаторами.

## Краткое описание продукта

Система принимает исследовательский вопрос и список стартовых URL сайтов финансовых регуляторов, автоматически проходит цепочку

```
URL → Page → Links → Documents → Text → Relevant Evidence
```

и возвращает структурированный JSON + человекочитаемый Markdown-отчёт, в котором каждый существенный факт снабжён ссылкой на источник (для PDF — с номером страницы).

Предметная область — макропруденциальное регулирование: контрциклический буфер капитала (CCyB), буфер системного риска (SyRB), системно значимые организации (D-SIB / O-SII), буфер консервации капитала, LTV/DSTI/DTI-ограничения, LCR/NSFR. Домен важен как источник тестовых данных и терминологии; система при этом остаётся предметно-нейтральным поисковым конвейером — специфической логики расчёта буферов ПЗ не требует.

Цель первого этапа сформулирована в ПЗ §26 буквально: доказать, что система способна пройти путь от исходной страницы до релевантного вложенного первоисточника и извлечь из него evidence.

## Границы проекта

**Входит в MVP** (ПЗ §4): HTML, PDF с текстовым слоем, обычные hyperlinks, внутренние и внешние ссылки, английский язык, ограниченный рекурсивный обход (depth ≤ 2), текстовый анализ LLM, структурированный JSON-вывод, Markdown-отчёт, CLI-запуск.

**Не входит в MVP** (ПЗ §4, §26): браузер с JS-автоматизацией, обход CAPTCHA, авторизация на сайтах, OCR сканов, DOCX, XLSX, граф знаний, автоматическое сравнение десятков стран, multi-agent orchestration, сложный reranking, vector DB, scheduled monitoring, автообновление данных, production-UI, поиск по всему интернету, гарантия полноты исследования, разрешение конфликтов между источниками.

Ограничение архитектуры (ПЗ §4): невходящие возможности должны быть добавляемы позже без переписывания ядра — но реализовывать их на этапе 1 запрещено.

## Используемые статусы

Единый набор для всех документов `docs2/`:

| Статус | Значение |
|---|---|
| `DONE` | Реализовано и соответствует требованиям |
| `PARTIAL` | Реализована только часть |
| `READY` | Решений достаточно для начала разработки |
| `IN_PROGRESS` | Работа начата |
| `BLOCKED` | Требуется внешнее решение (OQ) |
| `EXTERNAL` | Результат предоставляет другая команда / внешняя система |
| `REUSABLE` | Старую реализацию можно адаптировать |
| `LEGACY-AS-IS` | Существует в коде, но не является целевым |
| `PROPOSAL` | Техническое предложение, ещё не утверждено |
| `NOT_STARTED` | Подтверждено, но не реализовано |

Статусы решений (`decisions.md`): `CONFIRMED`, `PROVISIONAL`, `BLOCKED`, `SUPERSEDED`.

На 2026-09-02 появился статус `PARTIAL` (T-001, T-006, T-007, T-008, T-009). `DONE`, `IN_PROGRESS`, `REUSABLE`, `LEGACY-AS-IS` не встречаются: ни одна задача не удовлетворяет своим критериям готовности целиком. Статус `SUPERSEDED` появился 2026-08-31 у D-005 и D-015 после получения ответов на OQ-001 и OQ-002.

**`PARTIAL` здесь не означает «почти готово».** Для T-006…T-008 он означает «код написан, но блокеры не сняты и критерии не выполнены» — такую задачу нельзя ни считать закрытой, ни расширять до ответа на её OQ.
