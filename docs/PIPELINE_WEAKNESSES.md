# Известные уязвимости и недостатки пайплайна

По трём живым прогонам главный вывод: текущая taxonomy годится как консервативный генератор кандидатов, но пока не как точный фильтр для автоматического обхода. Она даёт много ложноположительных ссылок и иногда теряет потенциально полезные документы через `UNKNOWN`.

Логи:

- [ESRB CCoB](../regulatory-research-agent/data/results/esrb_pipeline_run.log)
- [OSFI LTI](../regulatory-research-agent/data/results/osfi_lti_pipeline_run.log)
- [MNB LCR/NSFR](../regulatory-research-agent/data/results/mnb_lcr_nsfr_pipeline_run.log)

Во всех трёх случаях использовался один вопрос про CCyB.

## Сводка прогонов

| Seed | Ссылок | HIGH | POTENTIAL | NAV | IRRELEVANT | UNKNOWN | Кандидатов |
|---|---:|---:|---:|---:|---:|---:|---:|
| ESRB CCoB | 171 | 21 | 35 | 71 | 2 | 42 | 56 |
| OSFI LTI | 30 | 0 | 3 | 24 | 3 | 0 | 3 |
| MNB LCR/NSFR | 131 | 17 | 67 | 39 | 7 | 1 | 84 |
| Итого | 332 | 38 | 105 | 134 | 12 | 43 | 143 |

43% всех ссылок стали кандидатами, хотя две из трёх страниц посвящены другим инструментам.

# Подтверждённые проблемы качества

## 1. Seed-страница вообще не классифицируется

Пайплайн проверяет только ссылки, найденные внутри seed. Он не отвечает:

```text
Соответствует ли сама исходная страница исследовательскому вопросу?
```

Поэтому OSFI LTI и MNB LCR/NSFR полностью обработались по вопросу про CCyB, хотя их основная тема другая.

Последствие: ошибочно переданный seed создаёт кандидатов вместо раннего результата `SEED_IRRELEVANT`.

## 2. Нет соответствия `seed -> research_question`

Исходный список содержит страницы про:

- CCyB;
- CCoB;
- LTI;
- LCR/NSFR;
- O-SII;
- другие инструменты.

Но текущий запуск принимает один вопрос. Если одним CCyB-вопросом обработать весь список, большая часть классификации будет методологически некорректна.

Нужно либо группировать seed по вопросам, либо хранить явное соответствие:

```text
seed_url -> research_question -> expected instrument
```

## 3. Одного общего слова достаточно для `direct`

[`_topic_match()`](../regulatory-research-agent/app/taxonomy.py) считает совпадение прямым, если найден любой термин вопроса.

Вопрос содержит `rate`, поэтому:

```text
Exchange rates    -> direct -> HIGH_VALUE
Base rate history -> direct -> HIGH_VALUE
```

На ESRB файл с заголовком `Current and pending CCoB rates` тоже стал `HIGH_VALUE` для вопроса про CCyB.

Нет требования, чтобы одновременно совпал ключевой инструмент `CCyB`.

## 4. Не различаются финансовые инструменты

Прогоны показали смешивание:

```text
CCyB-вопрос
  <-> CCoB data
  <-> LCR regulation
  <-> NSFR regulation
  <-> exchange rates
```

Это прямо противоречит цели проекта различать CCyB, CCoB, O-SII, SyRB, LCR и другие инструменты.

Причина: классификатор ищет отдельные слова, но не выделяет обязательную сущность вопроса.

## 5. Любая предметная лексика даёт `partial` независимо от вопроса

Слова `lcr`, `nsfr`, `financial stability`, `systemic risk`, `capital buffer` находятся в общей `domain_vocabulary`.

Поэтому документ про LCR получает `partial` при вопросе про CCyB:

```text
Commission Delegated Regulation (EU 2015/61)
-> regulatory_decision + partial
-> HIGH_VALUE
```

Фактически `partial` сейчас означает «относится к широкой макропруденциальной области», а не «частично отвечает на конкретный вопрос».

## 6. Матрица слишком щедра при `topic_match = none`

Матрица сохраняет первичные и вторичные типы документов даже без тематического совпадения:

```text
primary x none   -> POTENTIALLY_RELEVANT
secondary x none -> POTENTIALLY_RELEVANT
```

На полностью нерелевантной OSFI LTI-странице кандидатами стали:

```text
Consultations
Data and forms
News releases
```

Это глобальные разделы сайта, а не материалы по CCyB.

## 7. Правило навигации применяется не ко всем ссылкам меню

P-3 работает только для групп:

```text
undefined
navigation
related_material
```

Если ссылка внутри `<nav>` распознана как:

```text
data
research
financial_report
regulatory_decision
topic_landing
```

она обходит P-3 и становится кандидатом.

Это основная причина 84 кандидатов из 131 на MNB. Например, многочисленные пункты мегаменю `Research papers`, `Reports`, `Data` сохраняются намеренно.

## 8. Контекст ссылки может содержать весь блок меню

`surrounding_text` берётся из ближайшего `li/div/section` и обрезается до 300 символов. На сложной вёрстке ближайший блок может содержать десятки соседних ссылок.

На ESRB пустая self-ссылка получила:

```text
Legal framework -> group methodology
Systemic Risk   -> topic_match partial
primary x partial -> HIGH_VALUE
```

То есть признаки соседних пунктов меню были ошибочно приписаны пустой ссылке.

## 9. Generic anchor обрабатывается до навигации

Для `Download`, `More information`, пустого anchor сначала выполняется P-4. Если контекст не даёт группу, функция немедленно возвращает `UNKNOWN`.

Это может мешать P-3 корректно назвать ссылку навигационной. На ESRB встретились:

```text
пустой anchor -> UNKNOWN
Download      -> UNKNOWN
```

## 10. Один URL классифицируется несколько раз

Дедупликация выполняется по паре:

```python
(target_url, anchor_text)
```

Одинаковый PDF может присутствовать как:

```text
Notification by ...
English
Download
```

Каждая версия считается отдельной ссылкой и может получить другой класс. На ESRB один и тот же документ по описательному anchor получал `HIGH_VALUE`, а по anchor `English` — `UNKNOWN`.

Последствия:

- завышается количество кандидатов;
- один target URL получает противоречивые метки;
- будущий бюджет обхода расходуется повторно.

## 11. Нет агрегации нескольких свидетельств одного URL

Сейчас отсутствует правило вроде:

```text
один canonical URL
-> объединить все anchors и контексты
-> выбрать наиболее информативную классификацию
```

Классифицируются DOM-вхождения, а не уникальные документы.

## 12. Self-links остаются кандидатами

На MNB кнопки:

```text
Instagram
Twitter
Facebook
YouTube
Sellsy
Vissza a tetejére
```

ведут не на социальные сети, а на текущую seed-страницу. Поэтому P-1 не срабатывает, и они становятся `POTENTIALLY_RELEVANT`.

Нужен отдельный фильтр:

```text
target canonical URL == current/visited URL
-> SELF_LINK
```

## 13. Обнаружен некорректно собранный URL

На MNB появился URL:

```text
.../the-macroprudential-toolkit/www.mnb.hu/web/en/financial-stability/...
```

Вероятно, исходный `href` содержит домен без схемы, а `urljoin()` воспринимает его как относительный путь.

Ссылка стала внутренним кандидатом, хотя URL фактически повреждён.

## 14. URL-паттерны могут совпадать с началом другого слова

Для URL нет правой границы токена. Это сделано ради:

```text
methodolog -> methodology
```

Но создаёт побочные совпадения. На MNB:

```text
/mnb-data-reporting
-> паттерн report
-> group financial_report
```

`Information for data suppliers` стало первичным финансовым отчётом, хотя это страница для поставщиков отчётности.

## 15. Tie-break может давать неверную семантическую группу

При нескольких сильных совпадениях побеждает группа, расположенная раньше в YAML.

Например press release с `regulation` в URL может стать:

```text
regulatory_decision
```

вместо:

```text
official_information
```

Итоговый класс иногда совпадает, но объяснение и приоритет документа становятся неверными.

## 16. Высокая доля `UNKNOWN` на реальной странице

ESRB:

```text
42 UNKNOWN из 171 = 24,6%
```

Тестовый порог <=10% применяется только к evaluation dataset, но живой прогон показывает недостаточность справочника.

Среди `UNKNOWN` были PDF-уведомления, которые потенциально могут быть важными документами.

## 17. `UNKNOWN` полностью исключается из кандидатов

[`candidates()`](../regulatory-research-agent/app/taxonomy.py) оставляет только два класса:

```text
HIGH_VALUE
POTENTIALLY_RELEVANT
```

Если важный PDF получил `UNKNOWN` из-за anchor `English` или `Download`, он будет потерян для дальнейшего исследования.

## 18. Англоязычная таксономия

Нормализация вопроса использует:

```python
[a-z0-9-]+
```

Словари и синонимы тоже английские. На многоязычных страницах это приводит к зависимости от английской версии URL.

В логах уже встречаются:

```text
Български
Čeština
Magyar
Vissza a tetejére
Süti tájékoztatónkat
```

Для русского или другого неанглийского исследовательского вопроса тематическое сопоставление существенно деградирует.

## 19. Распознавание DOM-навигации неполное

Навигация определяется только по:

- тегам `nav`, `header`, `footer`;
- `role="navigation"`;
- классу, содержащему `breadcrumb`.

Современный сайт может использовать обычный `<div class="menu">`. Тогда ссылка получит контейнер `body/list/main`, и P-3 не сработает.

На ESRB ссылки `Skip to navigation/content/footer` получили `UNKNOWN`, а не `NAVIGATION`.

## 20. `section_heading` может относиться к другому блоку

Используется просто предыдущий `h1–h6` во всём документе. Структурная принадлежность заголовка и ссылки не проверяется.

На сложной странице ссылка может получить заголовок предыдущей секции или скрытого модального окна.

## 21. Несогласованное вычисление темы страницы

Документация определяет:

```text
source_page_topic = title + h1
```

Текущий [`main.py`](../regulatory-research-agent/app/main.py) передаёт только `title`.

Пакетный экспортёр уже использует `title + h1`. Поэтому одна и та же ссылка может классифицироваться по-разному в двух точках запуска.

## 22. Поддомены считаются внешними

`same_domain` — строгое равенство `netloc`.

Поэтому:

```text
www.mnb.hu
statisztika.mnb.hu
aszp.mnb.hu
```

считаются разными доменами, хотя принадлежат одной организации. Сейчас часть эффекта компенсирует список авторитетных доменов, но сам признак семантически неточен.

## 23. Список авторитетных и запрещённых доменов ручной

Проблемы:

- официальный регулятор, которого нет в allowlist, будет понижен;
- новый социальный домен или сокращатель ссылок не будет исключён;
- share-кнопка, ведущая через собственный домен, обойдёт исключение;
- организационная принадлежность поддоменов не определяется автоматически.

# Ограничения полноты пайплайна

## 24. Найденные документы не загружаются

Текущий процесс заканчивается после:

```text
Page -> Links -> Classes
```

Он не выполняет:

- depth-1 переход;
- загрузку PDF;
- извлечение текста;
- поиск evidence;
- проверку ответа на вопрос.

Поэтому `HIGH_VALUE` пока означает только «перспективная ссылка», а не подтверждённый источник.

## 25. `HIGH_VALUE` может быть неподдерживаемым форматом

В прогонах `HIGH_VALUE` получили XLSX-файлы. Классификация по спецификации корректна, но текущий MVP не умеет их обрабатывать.

Получается:

```text
HIGH_VALUE
-> невозможно извлечь текст текущим пайплайном
```

Нужен отдельный статус поддерживаемости формата.

## 26. Нет crawl budget и приоритета внутри класса

На MNB найдено 84 кандидата при проектном лимите 50 документов.

Внутри `HIGH_VALUE` нет дополнительного порядка:

- прямой документ;
- страница раздела;
- self-link;
- отчёт;
- data-файл.

Без ранжирования выбор первых 50 будет зависеть от порядка HTML.

## 27. Нет visited-URL множества

Это приводит к:

- self-links;
- повторным документам;
- потенциальным циклам;
- повторному расходованию бюджета.

## 28. Нет JavaScript-rendering

Обрабатывается только исходный HTML. Ссылки и данные, добавляемые JavaScript, не будут обнаружены.

Особенно это важно для интерактивных карт, таблиц и виджетов регуляторов.

## 29. Декодирование HTML всегда считается UTF-8

[`link_extractor.py`](../regulatory-research-agent/app/link_extractor.py) декодирует:

```python
html.decode("utf-8", errors="ignore")
```

Заявленная сервером кодировка не используется. На не-UTF-8 странице символы могут тихо исчезнуть, меняя anchor и результат классификации.

## 30. P-0 не оставляет трассировку

`classify_all()` просто удаляет игнорируемые ссылки. В штатном логе нельзя узнать:

- сколько ссылок отброшено;
- какие именно;
- почему.

Новый CSV-экспортёр компенсирует это отдельно, но базовый классификатор по-прежнему не возвращает результат P-0.

# Надёжность и наблюдаемость

## 31. `main.py` не проверяет HTTP 4xx/5xx

`fetch_url()` возвращает статус, но `main.py` продолжает обработку любого HTML.

Страница ошибки `404` или `403`, если она имеет `text/html`, может быть распарсена и классифицирована как обычная seed-страница.

## 32. Ошибка завершает весь одиночный прогон

В `main.py` нет обработки исключений вокруг:

- HTTP;
- парсинга;
- классификации.

Один timeout или неожиданный HTML завершит процесс traceback’ом.

## 33. Нет retry, backoff и контроля частоты запросов

При пакетном использовании возможны:

- потери из-за временного `503`;
- блокировки со стороны сайтов;
- лишняя нагрузка на регуляторов.

## 34. Нет ограничения размера ответа

`httpx` загружает весь ответ в память через `response.content`. Очень большой или специально сформированный HTML может вызвать чрезмерное потребление памяти.

## 35. Логи неструктурированные

Текущий вывод рассчитан на чтение человеком:

```text
[CLASS] anchor -> URL
    rule: reason
```

Нет:

- JSON logging;
- run ID;
- времени этапов;
- количества ссылок до P-0;
- стабильного идентификатора документа;
- структурированных `group` и `topic_match`.

`group` и `topic_match` приходится извлекать из строки `reason`.

# Риски безопасности

Эти риски не эксплуатировались в трёх прогонах, но следуют из того же текущего пути исполнения.

## 36. Возможен SSRF через seed URL

[`fetch_url()`](../regulatory-research-agent/app/fetcher.py) принимает произвольный URL и сразу отправляет запрос.

Если seed приходит от пользователя, можно попробовать обратиться к:

```text
localhost
127.0.0.1
внутренним корпоративным адресам
cloud metadata endpoints
```

Нет проверки публичности IP или запрещённых сетевых диапазонов.

## 37. Redirect может привести во внутреннюю сеть

`follow_redirects=True`, но каждый новый адрес перенаправления не валидируется. Даже разрешённый публичный URL потенциально может перенаправить запрос на внутренний адрес.

## 38. Ресурсное истощение

Нет ограничений на:

- размер HTML;
- количество HTML-узлов;
- количество ссылок;
- длину текста до парсинга;
- общий срок выполнения одного исследования.

Злонамеренная или просто огромная страница может создать нагрузку на память и CPU.

# Что исправлять первым

Приоритетный минимальный порядок:

1. Ввести `seed relevance gate` и соответствие `seed -> question/instrument`.
2. Требовать совпадения основного инструмента для `direct`; `rate` не должно быть достаточно.
3. Отделить «широкая предметная область» от совпадения с конкретным вопросом.
4. Агрегировать ссылки по canonical target URL до классификации.
5. Отсекать self/visited URL.
6. Исправить P-3: навигационный контейнер должен сильнее влиять на все группы.
7. Ограничить шумный `surrounding_text`.
8. Выделить `group` и `topic_match` в структурированный результат.
9. Добавить SSRF-защиту, проверку статусов и лимит размера ответа.
10. Только после этого подключать depth-1 обход и бюджет 50 документов.
