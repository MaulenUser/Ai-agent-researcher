# Дополнение к ПЗ №1: правила scoring, evidence и web crawling

## 12.1. Связь `relevance_score` и `relevance`

Для оценки релевантности документа используется одно числовое поле:

```json
{
  "relevance_score": 0.91
}
```

`relevance_score` принимает значение:

```text
0.0 <= relevance_score <= 1.0
```

и означает степень семантической релевантности документа исследовательскому вопросу.

Важно:

> `relevance_score` не является статистически откалиброванной вероятностью.

Например:

```text
0.91
```

не означает:

```text
91% probability that the document is relevant
```

На MVP это нормализованная оценка semantic relevance, которую возвращает LLM.

### Класс `relevance`

LLM **не должен независимо генерировать** одновременно:

```json
{
  "relevance": "high",
  "score": 0.91
}
```

Иначе возможны противоречия вида:

```json
{
  "relevance": "low",
  "score": 0.91
}
```

LLM возвращает только:

```json
{
  "relevance_score": 0.91,
  "reason": "The document contains methodology for setting the CCyB rate."
}
```

После этого приложение детерминированно вычисляет класс.

Для MVP установить следующие первоначальные пороги:

```text
HIGH:
0.75 <= score <= 1.00

MEDIUM:
0.45 <= score < 0.75

LOW:
0.00 <= score < 0.45
```

То есть:

```python
if score >= 0.75:
    relevance = "HIGH"
elif score >= 0.45:
    relevance = "MEDIUM"
else:
    relevance = "LOW"
```

Пример:

```json
{
  "relevance_score": 0.91,
  "relevance": "HIGH"
}
```

### Кто задаёт пороги

Пороги задаёт **приложение**, а не LLM.

Они должны находиться в конфигурации:

```yaml
relevance:
  high_threshold: 0.75
  medium_threshold: 0.45
```

На MVP значения 0.75 / 0.45 считаются стартовыми инженерными параметрами.

После создания размеченного validation dataset пороги должны быть откалиброваны эмпирически.

Например, следует проверить:

* precision HIGH;
* recall HIGH + MEDIUM;
* количество пропущенных релевантных документов;
* стоимость обработки MEDIUM документов.

До такой калибровки значения 0.75 и 0.45 не следует считать научно обоснованными.

### Использование классов

```text
HIGH
→ анализировать обязательно

MEDIUM
→ анализировать, если не превышены лимиты crawl/research

LOW
→ не отправлять на полноценный evidence extraction
```

LOW-документ при этом не удаляется из research log.

# 13.1. Определение `confidence` для evidence

Поле:

```json
"confidence": 0.94
```

в первоначальном ПЗ является неоднозначным.

В MVP его необходимо заменить на более точное:

```json
"support_score": 0.94
```

`support_score` отвечает только на вопрос:

> Насколько приведённый fragment/quote непосредственно подтверждает сформулированный claim?

Это **не**:

* вероятность истинности claim;
* вероятность модели;
* relevance документа;
* оценка авторитетности сайта;
* общий confidence LLM.

Например:

```json
{
  "claim": "The positive-neutral CCyB rate is 1%.",
  "quote": "The positive neutral CCyB rate is set at 1 per cent.",
  "support_score": 0.98
}
```

---

## 13.2. Как вычисляется `support_score`

Evidence extraction выполняется в два логических шага.

### Шаг A — Extraction

LLM формирует:

```json
{
  "claim": "...",
  "quote": "...",
  "source_url": "...",
  "page": 9
}
```

### Шаг B — Verification

Отдельный verification prompt получает:

```text
research question
claim
exact evidence fragment
surrounding context
```

и отвечает:

```json
{
  "support_score": 0.94,
  "verification_reason": "...",
  "status": "SUPPORTED"
}
```

Желательно, чтобы verification являлся отдельным LLM-вызовом.

На MVP допустимо использовать ту же модель, но:

* отдельный prompt;
* temperature = 0;
* без доступа к первоначальному reasoning extraction-stage.

Таким образом extraction и verification логически разделены.

---

## 13.3. `support_score` не зависит напрямую от `relevance_score`

Запрещается вычислять:

```text
support_score = relevance_score
```

или:

```text
support_score =
relevance_score × какое-либо число
```

Это разные величины.

Например документ может быть очень релевантен теме:

```text
document relevance = 0.96
```

но конкретная найденная цитата может лишь косвенно подтверждать claim:

```text
support_score = 0.52
```

И наоборот.

---

## 13.4. Пороги evidence

Для MVP:

```text
SUPPORTED
support_score >= 0.80

WEAK_SUPPORT
0.60 <= support_score < 0.80

UNSUPPORTED
support_score < 0.60
```

Правила:

### `SUPPORTED`

Может использоваться для итогового ответа.

### `WEAK_SUPPORT`

Сохраняется в research data, но не используется как единственное доказательство существенного claim.

Можно:

* искать второй источник;
* искать более точный fragment;
* вывести в `unresolved_findings`.

### `UNSUPPORTED`

Не включается как доказательство в итоговый отчёт.

# 13.5. Итоговая evidence schema

Использовать единообразную схему:

```json
{
  "claim_id": "claim_001",

  "claim": "The CNB uses a positive-neutral CCyB framework.",

  "source_url": "https://...",

  "document_title": "The CNB's approach...",

  "page": 9,

  "quote": "...",

  "support_score": 0.96,

  "verification_status": "SUPPORTED"
}
```

Поле `support_score` является обязательным для evidence, прошедшего verification.

Таким образом ошибка первоначального §14 устраняется: `support_score` должен присутствовать и в evidence внутри итогового JSON.

---

# 13.6. Что считается существенным claim

Термин «существенный claim» заменить на формальное определение:

> **Factual claim** — проверяемое утверждение о предметной области, которое используется для ответа на research question либо влияет на итоговый вывод системы.

К factual claims относятся, например:

### Числовые утверждения

```text
CCyB = 1%
O-SII buffer = 2%
```

### Даты

```text
The framework was introduced in June 2024.
```

### Текущее состояние

```text
The current CCyB rate is 1.25%.
```

### Будущие решения

```text
The rate will increase to 1.5% from 1 July 2027.
```

### Определения

```text
The CNB refers to the standard CCyB rate as a positive-neutral rate.
```

### Регуляторные решения

```text
Banco de España adopted a positive-neutral CCyB framework.
```

### Причины и обоснования

```text
The buffer is accumulated in normal times to create releasable capital.
```

### Сравнения

```text
17 EEA jurisdictions use or plan to use positive-neutral frameworks.
```

Каждый такой claim должен иметь evidence.

---

# 13.7. Разрешены ли factual claims без источника

В итоговом аналитическом ответе:

> **Нет.**

Domain factual claim без источника не должен подаваться пользователю как установленный факт.

Если система сформировала claim, но не нашла достаточного evidence:

```json
{
  "claim": "...",
  "status": "UNSUPPORTED",
  "evidence": []
}
```

он помещается в:

```json
"unresolved_claims": []
```

Например:

```json
{
  "claim": "The Czech Republic formally introduced PN CCyB in 2019.",
  "status": "UNRESOLVED",
  "reason": "A document states 'since about 2019', but an exact adoption decision has not yet been identified."
}
```

В итоговом тексте такой факт нельзя преобразовывать в:

```text
The Czech Republic introduced PN CCyB in 2019.
```

Допустимая формулировка:

```text
The reviewed source indicates that the concept has been used since approximately 2019; the exact adoption decision was not identified.
```

с указанием найденного источника.

---

# 13.8. Какие утверждения могут не иметь `source_url`

Ссылки на внешний источник не требуются для внутренних технических утверждений системы.

Например:

```text
18 URLs were checked.
7 PDFs were discovered.
3 URLs returned HTTP 404.
The crawler stopped at depth 2.
No supporting evidence was found.
```

Это не domain claims.

Для них источником является собственный execution log системы.

При необходимости использовать:

```json
{
  "provenance": "system"
}
```

Таким образом следует различать:

```text
DOMAIN CLAIM
→ source/evidence обязательно

SYSTEM CLAIM
→ execution provenance
```

# 21. Web crawling policy

## 21.1. `robots.txt`

Crawler должен по умолчанию соблюдать Robots Exclusion Protocol.

До обхода нового host необходимо проверить:

```text
https://<host>/robots.txt
```

и определить, разрешён ли доступ для User-Agent crawler.

RFC 9309 устанавливает стандарт Robots Exclusion Protocol. При успешной загрузке `robots.txt` crawler должен соблюдать применимые правила `Allow` / `Disallow`. При этом сам RFC отдельно отмечает, что robots.txt не является механизмом авторизации доступа.

Поэтому:

```text
robots.txt allows
```

не означает автоматически:

```text
legal permission to reuse any content
```

---

# 21.2. User-Agent

Запрещено маскировать crawler под Chrome, Firefox или другой обычный браузер.

Использовать собственный идентифицируемый User-Agent.

Например:

```text
RegulatoryResearchBot/0.1
```

Для production желательно:

```text
RegulatoryResearchBot/0.1 (+https://example.org/bot)
```

или контакт:

```text
RegulatoryResearchBot/0.1 (contact: research@example.org)
```

RFC 9309 рекомендует, чтобы идентификация User-Agent описывала назначение crawler, а product token совпадал с идентификатором, используемым для выбора группы в robots.txt.

В конфигурации:

```yaml
crawler:
  user_agent: "RegulatoryResearchBot/0.1"
  robots_product_token: "RegulatoryResearchBot"
```

---

# 21.3. Rate limiting

Для MVP установить консервативный default:

```yaml
crawler:
  per_host_concurrency: 1
  min_delay_seconds: 2.0
  global_concurrency: 4
```

То есть для одного host:

```text
request
↓
минимум 2 секунды
↓
следующий request
```

Не отправлять несколько параллельных запросов одному регулятору.

Это значение должно быть configurable.

---

# 21.4. Реакция на ограничения сервера

При:

```text
HTTP 429
```

обязательно соблюдать:

```text
Retry-After
```

если header присутствует.

При:

```text
429
503
network errors
```

использовать exponential backoff.

Например:

```text
2 sec
4 sec
8 sec
16 sec
```

с ограничением количества попыток.

Пример:

```yaml
retry:
  max_attempts: 4
  initial_backoff_seconds: 2
  max_backoff_seconds: 30
```

Если сайт продолжает ограничивать crawler, обработку данного host остановить.

---

# 21.5. `robots.txt` caching

`robots.txt` можно кэшировать.

По умолчанию:

```text
robots cache TTL = 24 hours
```

Это согласуется с RFC 9309, который рекомендует не использовать cached robots.txt более 24 часов при обычной доступности ресурса.

---

# 21.6. Ошибки при получении robots.txt

Для MVP использовать поведение, близкое к RFC 9309.

### robots.txt → HTTP 2xx

Прочитать и соблюдать правила.

### robots.txt → 4xx

Считать robots.txt недоступным и разрешить обычный public crawl, если нет других ограничений.

### robots.txt → 5xx / network failure

Использовать fail-closed:

```text
crawl host = blocked temporarily
```

RFC 9309 различает unavailable и unreachable robots.txt: при серверной/сетевой недоступности crawler должен считать доступ запрещённым, пока ситуация не разрешится.

---

# 21.7. Sitemap

Если robots.txt содержит:

```text
Sitemap:
```

система может использовать sitemap как дополнительный источник discovery.

Sitemap не заменяет обычный link discovery.

---

# 21.8. Правовые ограничения

Текущее ПЗ **не означает, что юридическая допустимость массового автоматического обхода всех сайтов уже согласована**.

Для MVP следует принять консервативную политику.

Разрешено исследовать:

* публично доступные страницы;
* публичные PDF;
* официальные документы;
* официальные отчёты;
* публичные данные, доступные без авторизации.

Crawler не должен:

* обходить login;
* обходить CAPTCHA;
* обходить paywall;
* обходить технические access controls;
* использовать украденные credentials;
* искать скрытые/private endpoints;
* игнорировать явно установленный запрет доступа;
* осуществлять чрезмерную нагрузку на сайт.

Отдельно необходимо учитывать:

* Terms of Use конкретного сайта;
* copyright;
* database rights;
* требования к повторному использованию документов;
* применимое национальное и европейское законодательство.

`robots.txt` является техническим механизмом управления crawler access, а не юридической лицензией на использование контента; RFC 9309 прямо отмечает, что REP не является механизмом авторизации.

Поэтому статус MVP следует фиксировать как:

```json
{
  "legal_review_status": "NOT_COMPLETED"
}
```

Перед production-запуском или масштабным регулярным мониторингом необходимо провести отдельную проверку условий использования целевых сайтов.

---

# 21.9. Политика хранения контента

Для исследовательского MVP предпочтительно хранить:

```text
URL
metadata
document hash
parsed text for internal processing
short evidence excerpts
page numbers
timestamps
```

а не создавать публичную копию полного содержимого сайтов.

В отчётах пользователю отдавать:

* фактический вывод;
* короткий supporting excerpt;
* ссылку на оригинальный источник.

# 21.10. Итоговая crawler-конфигурация MVP

```yaml
crawler:
  user_agent: "RegulatoryResearchBot/0.1"
  robots_product_token: "RegulatoryResearchBot"

  respect_robots_txt: true
  robots_cache_ttl_hours: 24

  per_host_concurrency: 1
  global_concurrency: 4
  min_delay_seconds: 2.0

  max_depth: 2
  max_documents_per_seed: 20
  max_total_documents: 50

  retry:
    max_attempts: 4
    initial_backoff_seconds: 2
    max_backoff_seconds: 30

relevance:
  high_threshold: 0.75
  medium_threshold: 0.45

evidence:
  supported_threshold: 0.80
  weak_support_threshold: 0.60
```
