# ПЗ №1. MVP системы автоматического исследования веб-источников

## 1. Название проекта

**AI Research Agent for Regulatory Web Sources**

Рабочее название: **Regulatory Research Agent**.

---

## 2. Цель первого этапа

Разработать минимально работающую систему, которая принимает:

* исследовательский вопрос;
* список исходных URL;

после чего автоматически:

1. проверяет доступность URL;
2. загружает содержимое веб-страниц;
3. определяет тип ресурса;
4. извлекает основной текст страницы;
5. находит ссылки на вложенные и связанные материалы;
6. выделяет потенциально релевантные PDF и веб-страницы;
7. извлекает текст из PDF;
8. ищет в найденных материалах информацию, относящуюся к вопросу пользователя;
9. формирует структурированный результат со ссылками на источники.

На первом этапе система **не должна пытаться полностью заменить Deep Research агент**.

Основная задача MVP — построить надёжный pipeline:

**URL → Page → Links → Documents → Text → Relevant Evidence**

---

# 3. Пример задачи для системы

Вход:

```json
{
  "research_question": "Есть ли информация о переходе к positive-neutral countercyclical capital buffer?",
  "seed_urls": [
    "https://www.bde.es/...",
    "https://www.cnb.cz/...",
    "https://www.mnb.hu/..."
  ]
}
```

Система должна:

* открыть каждый URL;
* определить, что находится на странице;
* найти связанные документы;
* скачать и обработать релевантные PDF;
* найти информацию про:

  * CCyB;
  * positive-neutral;
  * positive cycle-neutral;
  * standard CCyB;
  * neutral rate;
  * releasable capital;
* показать, в каких документах найдена информация.

---

# 4. Границы MVP

## В MVP входит

Поддержка:

* HTML;
* PDF;
* обычных hyperlinks;
* внутренних ссылок сайта;
* внешних ссылок;
* английского языка;
* ограниченного рекурсивного обхода;
* текстового анализа LLM;
* структурированного JSON output.

## В MVP пока не входит

Не реализовывать на первом этапе:

* полноценный браузер с JavaScript automation;
* CAPTCHA bypass;
* авторизацию;
* OCR сложных сканов;
* DOCX;
* XLSX-анализ;
* граф знаний;
* автоматическое сравнение десятков стран;
* multi-agent orchestration;
* сложный reranking;
* vector DB;
* scheduled monitoring;
* автоматическое обновление данных;
* UI уровня production;
* поиск по всему интернету.

Архитектуру при этом строить так, чтобы эти возможности можно было добавить позже.

# 6. Этап 1. Проверка URL

Для каждого исходного URL система должна определить:

```json
{
  "url": "...",
  "status": "accessible",
  "http_status": 200,
  "final_url": "...",
  "content_type": "text/html",
  "domain": "cnb.cz"
}
```

Обрабатывать:

* HTTP 200;
* redirect;
* 404;
* 403;
* timeout;
* SSL error;
* unsupported content type.

Ошибки одного URL не должны останавливать обработку остальных.

---

# 7. Этап 2. Извлечение HTML

Из HTML необходимо извлекать:

* title;
* meta description;
* headings h1-h6;
* основной текст;
* ссылки;
* anchor text;
* URL ссылки.

Пример:

```json
{
  "title": "Countercyclical capital buffer",
  "headings": [
    "Countercyclical capital buffer",
    "Current CCyB rate",
    "Related documents"
  ],
  "text": "...",
  "links": [
    {
      "anchor": "Methodological framework",
      "url": "...pdf"
    }
  ]
}
```

Навигация, cookie banner, footer и прочий boilerplate по возможности должны удаляться.

---

# 8. Этап 3. Извлечение ссылок

Для каждой найденной ссылки сохранять:

```json
{
  "source_url": "...",
  "target_url": "...",
  "anchor_text": "Methodological framework",
  "extension": "pdf",
  "same_domain": true
}
```

---

# 9. Этап 4. Классификация ссылок

Система должна разделить ссылки минимум на четыре класса:

```text
HIGH_VALUE
POTENTIALLY_RELEVANT
NAVIGATION
IRRELEVANT
```

## HIGH_VALUE

Примеры anchor text:

```text
methodology
methodological framework
decision
official information
financial stability report
macroprudential report
press release
consultation
opinion
guidelines
technical note
research paper
annex
```

## POTENTIALLY_RELEVANT

Например:

```text
related documents
publications
archive
financial stability
macroprudential policy
capital buffers
```

## NAVIGATION

Например:

```text
home
contact
about
careers
language
privacy
```

# 10. Этап 5. Рекурсивный обход

На первом этапе использовать:

```text
max_depth = 2
```

Где:

```text
depth 0 = исходный URL
depth 1 = ссылки с исходной страницы
depth 2 = ссылки из найденных релевантных страниц
```

Необходимо также установить:

```text
max_documents_per_seed = 20
max_total_documents = 50
```

Для предотвращения бесконечного crawl.

Не переходить повторно по одному и тому же canonical URL.

---

# 11. Этап 6. Работа с PDF

Для PDF система должна:

1. скачать файл;
2. сохранить его URL;
3. извлечь текст;
4. определить количество страниц;
5. сохранить текст с привязкой к странице.

Формат:

```json
{
  "url": "...pdf",
  "title": "...",
  "pages": [
    {
      "page": 1,
      "text": "..."
    },
    {
      "page": 2,
      "text": "..."
    }
  ]
}
```

На MVP использовать PDF с текстовым слоем.

Если PDF является сканом:

```json
{
  "status": "ocr_required"
}
```

OCR пока можно не реализовывать.

---

# 12. Этап 7. Оценка релевантности

Для каждого документа необходимо оценить:

> Насколько этот документ может содержать ответ на research_question?

Выход:

```json
{
  "relevance": "high",
  "score": 0.91,
  "reason": "Document discusses countercyclical capital buffer methodology and neutral rate."
}
```

Возможные классы:

```text
HIGH
MEDIUM
LOW
```

LLM должен оценивать **смысл**, а не только точное совпадение слов.

Например:

```text
standard CCyB rate
```

должно считаться потенциально связанным с:

```text
positive-neutral CCyB
```

---

# 13. Этап 8. Поиск evidence

Из документов с HIGH/MEDIUM relevance система должна извлекать фрагменты, отвечающие на research_question.

Структура evidence:

```json
{
  "claim": "The CNB applies a standard CCyB rate of approximately 1%.",
  "source_url": "...",
  "document_title": "...",
  "page": 5,
  "quote": "...",
  "confidence": 0.94
}
```

Важно:

**каждый существенный claim должен иметь source_url.**

Если источник PDF — желательно сохранить номер страницы.

# 18. Что делает обычный код, а что делает LLM

## Код

Код отвечает за:

* HTTP;
* redirects;
* HTML parsing;
* PDF parsing;
* URL normalization;
* duplicate detection;
* recursion;
* file handling;
* limits;
* caching.

## LLM

LLM отвечает за:

* semantic relevance;
* понимание исследовательского вопроса;
* классификацию сложных ссылок;
* поиск смысловых эквивалентов;
* evidence extraction;
* synthesis.

Принцип:

> **Детерминированные задачи не отдавать LLM.**

# 19. Логирование

Каждое действие crawler должно логироваться.

Например:

```text
[FETCH] https://...
[200] HTML
[DISCOVERY] 42 links found
[FILTER] 8 potentially relevant
[FETCH PDF] methodology.pdf
[PARSE] 24 pages
[RELEVANCE] 0.94
[EVIDENCE] 4 claims extracted
```

Также сохранять ошибки.

---

# 20. Кэширование

Не загружать один URL повторно в рамках одного исследования.

Желательно сохранять локально:

```text
URL
fetch timestamp
status
content hash
parsed text
```

На MVP достаточно файлового cache или SQLite.

---

# 21. Безопасность crawler

Обязательно:

* timeout;
* max response size;
* max PDF size;
* max recursion depth;
* max number of URLs;
* URL normalization;
* запрет `file://`;
* запрет localhost/private IP;
* обработка redirects;
* whitelist `http/https`.

# 24. Acceptance Criteria

MVP считается выполненным, если система:

### AC-01

Принимает research question и массив seed URLs.

### AC-02

Корректно проверяет доступность минимум 90% тестовых URL.

### AC-03

Извлекает основной текст HTML.

### AC-04

Извлекает все обычные hyperlinks со страницы.

### AC-05

Обнаруживает PDF, находящиеся непосредственно на seed page.

### AC-06

Может перейти минимум на depth=2.

### AC-07

Извлекает текст из text-based PDF.

### AC-08

Определяет semantic relevance документа к research question.

### AC-09

Для Spain, Czech Republic и Hungary находит минимум один релевантный вложенный документ, которого нет в seed_urls.

### AC-10

Для найденных фактов возвращает source URL.

### AC-11

Для PDF evidence возвращает номер страницы, если он доступен.

### AC-12

Формирует JSON output.

### AC-13

Формирует Markdown research report.

# 25. Отдельный обязательный интеграционный тест

Для CNB дать системе только:

```text
https://www.cnb.cz/en/financial-stability/macroprudential-policy/the-systemic-risk-buffer/
```

Research question:

```text
Does the Czech National Bank use a positive-neutral CCyB framework?
```

Ожидаемое поведение:

```text
SyRB page
    ↓
SyRB methodology PDF
    ↓
finding:
"standard CCyB rate (or positive neutral rate)"
```

Это будет одним из ключевых тестов способности системы находить информацию **не только по прямому совпадению названия страницы**.

---

# 26. Что пока не требуется от MVP

MVP не обязан:

* гарантировать полноту исследования;
* самостоятельно искать новые сайты через Google/Bing;
* находить все источники по стране;
* строить knowledge graph;
* определять истину при конфликтующих источниках;
* поддерживать десятки форматов;
* выполнять постоянный monitoring.

Главная цель первого этапа:

> доказать, что система способна пройти путь от исходной страницы до релевантного вложенного первоисточника и извлечь из него evidence.
